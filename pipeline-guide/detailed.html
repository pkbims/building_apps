How to use this page

A walkthrough of the pipeline as it stands on 2026-09-24, read from PIPELINE.md, APP_GUIDE.md, PROGRESS.md and the eight skills in .claude/skills/.

Three parts:

  1. The pipeline: every stage from setting up the app to shipping it. For each one: the goal, what goes in, what comes out, which skill runs it, what you type, and the gate that ends it.
  2. The skills: each skill in detail, meaning its steps, its hard rules, the files it uses and the tradeoffs it records. Pipeline skills come first, then the skills that support the process.
  3. Reviewer's notes: gaps and inconsistencies I found while reading. Each one has a fix / leave / discuss choice.
Commenting. Hover any block and press comment. Pick Change request to have the page or a skill edited, Question to get an answer in the terminal, or Comment for anything you just want me to know. Nothing reaches me until you press Confirm & send. Once you have been through a skill with a real app, this is where your feedback on it goes.

The three rules behind every stage

  1. Claude never moves you to the next stage. Every transition needs a file you have looked at and a decision you have made.
  2. Each stage reads the previous stage's file, not the chat. A fresh or compacted session starts from whatever is on disk.
  3. The baseline in CLAUDE.md does not bend. That means real auth, a DB with migrations, Docker, CI/CD, tests that gate the pipeline, rate limiting, health checks, error tracking, logging, and metrics with a dashboard.

1Research

Skill: /research, then an html-worker review page. Runs before any app repo exists.

Goal

Prove the pain is real before building anything. Find out who already solves it, how they work, what they earn, and what their users complain about, then choose one direction.

Inputs

  • The problem in one line
  • Hard limits (which phone, must it fit the series stack)
  • Optional: Reddit threads you paste yourself (Reddit is blocked)

Outputs

  • Everything in building_apps/research/<niche>/, since there is no app repo yet
  • <niche>.md, ending in "Strongest option: X" and "Worth building? yes/no"
  • Review page in reviewer/, plus the pulled review JSON

Gate: two decisions on the page

  1. Which option is strongest, plus the 2–3 quotes for the Anchored-to block.
  2. Build it? No: the folder moves to archived_research/<niche>/ with a README saying why (toronto-student-rentals is the precedent). Yes: go to stage 2 and set the app up.

You type

/research knowledge workers on iPhone who lose focus to social media

The rule that never bends: no quote that wasn't read in this session. verify_quotes.py checks every quote against the raw JSON before the file counts as done.

2Set up, then positioning

No skill. PIPELINE §2 is the spec. It's a conversation loop, not a generated document.

Goal

Give the app its repo, now that it has earned one. Then decide what you are building and why anyone would pick it over what exists, in one paragraph the PRD must obey. Aim for adjacent and sellable, not original.

Inputs

  • The research folder, with a chosen option and a yes to "build it"
  • The 2–3 quotes you picked

Outputs

  • positioning.md: one paragraph naming the user, the closest existing product and the wedge
  • Anchored to block: 2–3 verbatim complaints plus a link to the research
  • The rest of app_N/CLAUDE.md: a paragraph on what it is, the constraints (each naming its research finding), and where things are

Gate

You react until one paragraph survives. Every candidate must fit "it's basically X, but Y", where X is a real shipping product. A candidate that can't is cut.

First: set up the app

mkdir app_N && cd app_N && git init
mv ../research/<niche> research

Write a first app_N/CLAUDE.md containing the problem in one line, the platform and hard limits, and Stack: series default plus any deviation with a reason. The constraints come after positioning. Commit the research.

You type

Positioning for app_N, from the research.

Claude proposes 2–3 candidates, one paragraph each. Don't skip the Anchored-to block. Stage 3 won't start without it, because it is the evidence that lets the PRD argue instead of assert.

Last: finish app_N/CLAUDE.md

This is the part set-up couldn't write yet. It holds the handful of decisions that constrain everything downstream, each naming the research finding behind it. app_3's list is the model: never more than three options; recipes curated, not generated; calories from ingredients, never a photo; nothing useful behind a sign-up wall.

3Spec: the PRD

Skill: /create-prd in HTML mode, on an html-worker page.

Goal

Turn the chosen problem into a spec someone could build from. The spec argues a case: the problem is real, therefore these requirements, therefore this experience, therefore this system. It must also name what is not being built.

Inputs

  • positioning.md with its Anchored-to block
  • The research file (for quotes)

Outputs

  • spec/index.html + state.json (the page, which is the source)
  • spec/prototype.html
  • spike/ results, if any bets needed testing
  • PRD.md, exported from the page

You say "done". Expect 3–6 rounds (app_1 and app_4 each took 10).

4Contract freeze

No skill. PIPELINE §4 is the spec. From here on Claude is the orchestrator.

Goal

Lock the API between client and backend so that two workers can build in parallel and neither can change what sits between them.

Inputs

  • PRD §15 (data model) and §16 (API contract)

Outputs

  • backend/app/schemas.py
  • Route signatures in backend/app/main.py, with empty bodies
  • contract/openapi.json, generated and never hand-edited
  • A CI contract check

Gate

Read the endpoint list, not the code. Does it match the screens from stage 3? If it does, commit. The contract is frozen from that commit on.

You type, and how the freeze is enforced

Freeze the contract from PRD §15-16.
  • CI regenerates the JSON and runs git diff --exit-code contract/openapi.json. Any drift fails the build.
  • Tooling: ruff and mypy exclude the frozen files, so a formatter can't fork them.
  • Ownership: workers can't edit them. The only way to change the contract is a numbered entry in ORCH-QUESTIONS.md.

5Build v1

No skill yet. It's the strongest skill candidate. This is the only stage that runs three sessions.

Goal

Build the whole baseline and the core app in parallel against the frozen contract, and end on a v1 date you can name.

Inputs

  • The frozen contract
  • PRD §17 (operations) and §18 (build order)
  • design/HANDOFF.md + tokens.json for the client

Outputs

  • HANDOFF.md, backend/AGENT.md, <client>/AGENT.md
  • ORCH-QUESTIONS.md
  • Both branches merged to main

Gate

At each checkpoint the orchestrator runs the tests and hits the endpoint itself before merging. Done when the client runs end to end against the real local backend and each half has its baseline items.

The three roles (one Herdr tab each)

TabCheckoutJob
orchestratormainWrites no app code. Writes the briefs, answers ORCH-QUESTIONS, merges at checkpoints, and verifies what workers claim instead of relaying it.

If a worker hits a contract problem, it appends Q3 — … to ORCH-QUESTIONS and moves on to other work. You decide the question, and the orchestrator regenerates the contract. Anything needing a device, an Apple ID or an entitlement is yours to do.

research

Stage 1Invoke /research <who> who <problem>File .claude/skills/research/SKILL.md · 189 lines
Problem→What already exists→The pattern (who, why, revenue)→Complaints→New ideas→Pick one

The six steps

  1. Write down the problem. One line, in plain words.
  2. Find every existing solution. Search the App Store, Google Play, "best X apps" articles (useful for names only) and forums.
  3. Find the pattern. For each solution: how it works step by step (3–6 steps, done first), who it's for, why that group, and money from a real source or "no public number". Then look across all of them: what they agree on, who nobody serves, where they all charge the same.
  4. Complaints. Verbatim quotes from Play, the App Store and Trustpilot. Three or more people saying the same thing is a pattern; one person is a bad day. Answer in one line whether each solution actually helps people.
  5. Brainstorm 1–3 new solutions. Each one fixes a named complaint. Check two things: can it be built, and could people find it? An idea that fails both is cut.
  6. Decide. Name the strongest option in one line and give an honest "worth building?" read, then stop. You pick the option, the quotes, and build or archive.

Hard rules

  • Never write a quote you did not read in this session. WebFetch summaries paraphrase, so each quote is checked against the raw pulled text.
  • No revenue number without a real source.
  • No hype words ("massive", "underserved", "game changer"), no summary that repeats what's above it, and no line that would still be true in a different niche.
  • Bullets rather than paragraphs.

Scripts, run in order

ScriptDoesReliability
play_reviews.py300 recent Google Play reviews per app, each with its own linkThe reliable source
appstore_reviews.py10 embedded reviews plus the RSS feed, with retriesWorks for some apps; no per-review links
verify_quotes.pyEvery "…" — [ quote must exist verbatim in the pulled JSONRun before calling the file done

Trustpilot blocks curl, so it's read in the browser via __NEXT_DATA__. Reddit is blocked everywhere.

Output and handover

It is written to building_apps/research/<niche>/<niche>.md, because no app exists yet. After a yes the folder moves into app_N/research/; after a no it goes to archived_research/. The file follows a fixed template: problem, a block per solution, the pattern, new ideas, a mermaid picture, and the decision. It is then shown as an html-worker review page with the option as a radio, the Anchored-to quotes as checkboxes, and "build it?" as its own radio. The terminal gets the URL and the list of decisions only.

create-prd

Stage 3Invoke /create-prd then "HTML mode"File .claude/skills/create-prd/SKILL.md · 194 lines
The case→The experience→Prototype→Design brief (3½)→Spike→The build→Export

Part 1: The case (§1–6)

  1. Summary: one paragraph covering what it is and the one thing others don't do.
  2. The problem: verbatim quotes with attribution. Evidence is never paraphrased.
  3. Design requirements R1, R2…, each with the evidence that forces it. This is the hinge, and it is written before any solution exists.
  4. Positioning: the wedge, in one paragraph.
  5. Who it's for: one audience.
  6. Scope: including an explicit list of what it does not do.

Part 2: The experience (§7–10)

  1. User flow end to end, with a diagram.
  2. Screens, clickable, with layout choices as decisions.
  3. Success criteria: one headline metric that measures the promise itself, with the percentile named.
  4. Accepted risks: the concrete failure, the requirement it breaks, who accepted it and when, and the mitigation.

Between Parts 2 and 3: the prototype

  • One prototype.html, served from the same directory. HOST=0.0.0.0 lets you open it on your phone, and it can also be published as a private Artifact.
  • It covers every screen in §8 and every path in §7, with the decisions so far baked in.
  • Styling follows platform conventions (on iOS: system font, inset lists, tab bar). It sits in a device frame on desktop and goes full-bleed on the phone.
  • It uses real sensors, each with a "simulate" fallback. Compressed time is printed on screen. State lives in browser storage and there's a reset.
  • It is not a backend, a build target or a design system. Claude says in the terminal which 2–3 places to watch while you use it.

Before §12: the spike

List every belief the mechanism rests on and sort it into two tables:

  • Spike: bets that would change the architecture if they failed. Each gets a throwaway spike/ project and a day.
  • Not spiked: documented capabilities that thousands of apps use daily. They're listed so nobody wonders, and never tested.

Why: app_1 wrote its mechanism first and spiked it afterwards. The spike disproved the mechanism, and the architecture was rewritten.

Part 3: The build (§11–19)

§11 TR1… · §12 architecture, covering every half · §13 vendor choices with rejected options · §14 the client (the framework, the hardest screen, tests, shipping) · §15 data model · §16 API contract · §17 operations · §18 build order, riskiest first · §19 open decisions.

The disciplines

  • Plain words. Every technical term gets an inline gloss the first time it appears, and every acronym is spelled out once.
  • Every technical decision is yours. Each is a radio with three plain lines per option and no pre-selection. Provisional picks go in §19.
  • Surface conflicts between answers that are each sensible alone, and raise each one as its own decision.
  • Both halves specified to the same depth. Count the decisions on each side.
  • Ask what the hardest screen requires. It drives the client stack.
  • Follow shipping requirements into every component, e.g. signing and store review on mobile.
  • Strike superseded decisions through, rather than leaving two products described in one document.
  • Export PRD.md from the page, never from a second narrative.

create-ui-design-direction

Stage 3½Invoke "Design brief for app_N."Files SKILL.md · references/questions.md · assets/BRIEF-template.md · scripts/check_brief.py
Check Part 2 holds→Pull generated blocks→Ask on a page→Rounds → "done"→Build BRIEF.md→Stop & hand over→Check the handoff

The principle: constrain the product, free the surface

  • Fixed: flow, screen list, states, contract strings, and token discipline.
  • Compass, not cage: the vibe (three words and a "not like"), references, and voice.
  • Left open, and the brief says so: motion, illustration, the one animated moment, and layout within a screen.

Why: app_1's mosaic sign-in was the screen that landed best, and it was the tool's own idea. Specifying hex values and fonts shuts that kind of idea out.

Step 1: pull the generated blocks from the PRD page (not PRD.md)

Brief sectionSource
§1 What this ispositioning paragraph, PRD §5, two Anchored-to quotes
§4 Screen inventoryPRD §8
§5 Fixed stringsPRD §16 if it exists; otherwise "propose error copy"
§10 Fixed vs openstate.json: answered ids are fixed, unanswered ones are built as switches

It also lists the screens the flow needs but §8 doesn't name (home, settings, account, sign-out, the "done" landing) and scans the app directory for real data such as photos.

Step 2: nine questions on an html-worker page

  1. Navigation model, and where "done" lands
  2. Device range
  3. Screens to add
  4. Vibe: three words, three candidate triads
  5. Like / not like
  6. Copy voice
  7. Real data files
  8. The two screens for the side-by-side directions
  9. Open for invention (checkboxes; anything unchecked isn't mentioned)

Stated as fixed rather than asked: light mode only for v1 (D5), accessibility handled at build (D6), tokens as the contract, two directions before any other screen, and the handoff shape.

Steps 3–4 and the return path

  • Fill BRIEF-template.md, then run check_brief.py. It fails on leftover placeholders, empty state cells, missing references, or a brief over 200 lines.
  • Stop. Tell you exactly what to attach to Claude Design and what to bring back. Update PROGRESS.md. Don't open the tool or draft screens.
  • Return: check that HANDOFF.md has its five sections, that tokens.json parses with every colour named, and that every screen is accounted for. Then Part 3 continues.

lowN7: PIPELINE.md's header is stale

lowN8: Research only knows app-store sources
The series ships web SaaS tools as well as iOS apps, but the review scripts only pull from Play and the App Store. A web tool's complaints live on G2, Capterra, Product Hunt and forums. This will bite on the first web app.
mediumN9: Ship (stage 7) is one line, and "v1" isn't "shipped"

doneN11: Research comes first, and setup only follows a "build it"
The old stage 0 asked for research findings before any research had happened, and no app ever followed it. Your call: research first, and set the app up only once you have confirmed it is worth building. Changed on 2026-09-24 in APP_GUIDE, PIPELINE §1–2 and the research skill. Research now lives in building_apps/research/<niche>/ and ends on a build-it gate: no goes to archived_research/, yes goes to stage 2, which opens with setup.
