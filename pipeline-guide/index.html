The pipeline in one line

What happens first, second, third, and so on. Click a step to jump to it.

1 · Problem→2 · Research→3 · Build it?→ 4 · Set up + Positioning→5 · PRD: case + v1 features→ 6 · Prototype + Design→7 · Spike + Build plan→ 8 · Build v1 → TestFlight→9 · Ship

Every step leaves a file on disk, and the next step reads that file, not the chat. You approve every move to the next step.

in skill / in guide means a skill or APP_GUIDE captures it. added 09-24 marks what we agreed on in chat and what got built into the skills on 2026-09-24. Orange boxes mark places where information is missing, which is where an assumption would sneak in.

2Research the problem and the apps that solve it

First, why the problem exists. Then who already solves it, how, for how much money, what their users complain about, and why they went viral.

Captures
  • Why the problem exists, every claim with a source added 09-24
  • Every existing app: how it works step by step, who it's for in skill
  • Each app's feature list, marking the features every app has added 09-24
  • MRR from a real source, or an estimate labelled as an estimate in skilladded 09-24
  • Verbatim complaints, checked by a script in skill
  • What made each app go viral, with a source added 09-24
  • 1–3 new ideas, each fixing a named complaint in skill
File
research/<niche>/<niche>.md + a review page (no app repo yet)
Settled 09-24: MRR comes from TrustMRR first (verified revenue), then Google search for founder posts and articles. Viral evidence comes from Google search.

3You decide: build it or not

You make three choices on the research review page.

You decide
  • The strongest option (an existing app to copy + a twist, or a new idea) in skill
  • The 2–3 complaint quotes that become your evidence in skill
  • Build it? Yes only if at least one app earns $10k+ MRR on this problem in skilladded 09-24
If no
The folder moves to archived_research/<niche>/ with a line saying why. Stop.
If yes
Go to step 4.

5PRD: the case, then the v1 features

The PRD argues why this should exist, then decides exactly what v1 contains.

Part 1 · case
The problem with quotes · numbered requirements R1, R2… each backed by evidence · one audience · what we're not building in skill
Part 2 · v1
  • v1 features, drafted from the features every competitor has + our USP + our viral feature added 09-24
  • Each feature: name → R# → screens → endpoints → risk added 09-24
  • Rule: a feature is v1 only if the promise breaks without it. The viral feature is always v1. Everything else is saved for later added 09-24
  • User flow · screens · one success metric · accepted risks in skill

6Feel it, then design it

7Test the risky features, then plan the build

Any feature we aren't sure will work gets a quick throwaway test first. Then the PRD says how every feature is built.

Spike
Risky features tested in spike/, with bets that affect every feature kept in a "shared" group in skilladded 09-24
Part 3 · build
Written from the spike results: architecture, vendor choices with rejected options, the client, data model, API contract, operations, build order. Every technical choice is yours in skill
File
PRD.md, exported from the page
↓

8Freeze the contract, build v1, ship it to TestFlight

The API is locked, then one orchestrator and two workers build the whole app at once.

Freeze
The API becomes code (contract/openapi.json), and CI fails if it changes in guide
Build
The orchestrator writes no code and verifies every merge. The backend and iOS workers each have their own worktree and build test-first in guide
Done
v1 is on TestFlight, talking to a real hosted backend added 09-24
