1Research

/research html-worker review page · status: real, run for app_2, app_3, app_4 · you type /research <niche + problem>

Why this stage exists: So nothing is built on a guess. Every later decision — the wedge, the requirements, the screens — has to point back at a real complaint from a real person. Research is where those complaints are collected, verbatim, with links.
Inputs
  • The problem, one line
  • Any hard limit (phone, series stack)
Asks for either if missing.
Does
Finds every existing solution, how each works, who it is for, revenue with a source, verbatim complaints, then 1–3 new ideas each fixing a real complaint.
Produces
<app>/research/<niche>.md in a fixed shape, then a review page in research/reviewer/.
Gate → Stage 2
File ends "Strongest option: X. Why: one line." and stops. You pick — on the page, as a radio. Stage 2 reads the file.
Inside /research — six steps, then write, then review
  1. Write down the problemgoal: one fixed target every solution is measured against · out: one plain line every solution below is trying to fix
  2. Find every solution that existsgoal: nothing we build already exists unnoticed · in: the problem line · where: App Store / Google Play search, "best X apps" articles (names only, not proof), forums · out: the full list, not two or three
  3. Find the pattern across themgoal: see what they all agree on and who nobody serves · in: the solution list · per solution: how it works in 3–6 steps (first, before anything), who it is for, why that group, money with a real source or "no public number" · then: what they agree on, who nobody serves, where they all charge the same
  4. Find what real users complain aboutgoal: the real failures, in users' own words, that a new idea must fix · in: each solution's store IDs · tools: play_reviews.py first (300 reviews/app, per-review links) → appstore_reviews.py (works for some) → Trustpilot via browser · rule: 3+ different people = pattern, one = a bad day · out: per solution, "actually helping? yes / kind of / no"
  5. Brainstorm 1–3 new solutionsgoal: candidates that answer a named complaint, not a vague idea · in: Step 4 complaints + platform limit · out: 1–3 ideas, each tagged "fixes: …" · each must: fix a specific Step 4 complaint, be buildable on the platform, be findable · fails both → cut
  6. Decide — then stopgoal: hand the choice to you with the options laid side by side · in: existing + new · out: "Strongest option: X. Why: one line." · lay out existing + new, name the strongest in one line. The user picks.
  7. Write the filegoal: one verified artefact a fresh session can pick up · out: research/<niche>.md · shape: problem → solutions (what / steps / who / money / quotes / helping?) → pattern → new ideas → mermaid picture → decision · run verify_quotes.py — every quote must exist verbatim in the pulled JSON
  8. Show it as an html-worker review pagegoal: your pick recorded as state, not chat · in: the file · out: state.json with the decisions · Step 6 choice as radio/checkbox blocks. Terminal reply = URL + list of decisions, nothing more. Standard decisions in practice: which failure is the wedge, which idea moves to Stage 2, which 2–3 quotes become the Anchored-to block.
The one rule that never bends: never write a quote you did not read this session. WebFetch summaries paraphrase, so every quote is checked against raw pulled text.

Not allowed in the file: hype words, invented money numbers, long paragraphs, a summary that repeats the above, any line that would still be true for a different niche.

4Contract freeze

no skill — PIPELINE §4 is the spec · no review surface: the gate is you reading the endpoint list in the terminal · status: prose, run once (app_1); app_4 is at this stage now · you type "Freeze the contract from PRD §15-16."

Why this stage exists: Two sessions can build in parallel only if neither can change the thing between them. Freezing the API as generated code — enforced by CI, tooling and ownership — is what makes Stage 5 possible.
Inputs
PRD §15 data model and §16 API contract. Claude now acts as orchestrator.
Does
Writes backend/app/schemas.py and empty route signatures in backend/app/main.py; export_openapi.py generates contract/openapi.json. The contract is code, not a document — never hand-edited.
Produces
openapi.json committed; CI step that regenerates and git diff --exit-code; ruff/mypy exclude the frozen files; ownership rule: workers may not edit them.
Gate → Stage 5
You read the endpoint list — not the code — against the Stage 3 screens. Match → commit. From then on the only change path is a numbered entry in ORCH-QUESTIONS.md. Done when both worker briefs point at the JSON.
The procedure as PIPELINE §4 gives it
  1. Schemas and route signatures from the PRDgoal: the contract exists only as code · in: §15–16 · out: schemas.py, main.py with empty bodies
  2. Generategoal: a JSON nobody hand-edits · in: schemas.py + main.py · out: backend/export_openapi.py → contract/openapi.json
  3. Enforce three waysgoal: drift cannot happen silently · out: CI drift check · tooling excludes · ownership (workers ask, never edit)
  4. You read the endpoint listgoal: you approve the shape without reading code · in: endpoint list vs. §8 screens · out: committed openapi.json · does POST /blocks, GET /blocks/{id}/status… match the screens? → commit → frozen

Stated tradeoff: the backend framework becomes the schema language, tying the contract to FastAPI/Pydantic pins — accepted because a hand-written spec drifts within a week and a generated one cannot.

Nothing contradictory found here. The PRD section numbers (§15, §16, §17) line up with create-prd's numbering.

5Build — one orchestrator, two workers

skill candidate — PIPELINE §5 is the spec · no review surface: orchestrator status summaries + ORCH-QUESTIONS.md · status: prose, run once (app_1, in progress: backend merged, iOS building) · three sessions, not one

Why this stage exists: To get both halves built against the contract, with every claim verified by someone who did not write the code. The orchestrator stays pure so it keeps checking instead of trusting.
Inputs
Frozen openapi.json, the PRD, and one AGENT.md brief per half. Workers are told: "Read AGENT.md and start."
Does
Orchestrator writes no app code. It writes HANDOFF.md, the briefs, creates worktrees on branches backend and ios, answers questions, verifies claims, merges at checkpoints. Workers build TDD-first in their own folder; the backend one builds the whole baseline as it goes.
Produces
main with both branches merged; the client running end to end against the real local backend; baseline items per half (PRD §17) in.
Gate → Stage 6
Each merge only after the orchestrator has run the tests and hit the endpoint itself — never relays "backend says done". You decide contract questions when pinged.
The files that make it work, and the question loop
  • HANDOFF.md — orchestrator context for a fresh session: roster, in flight, gotchas. Rewritten as things change; this is what lets the role survive a context reset.
  • <half>/AGENT.md — read order, what it owns, what it must not touch, the one rule (never edit the contract; ask in ORCH-QUESTIONS.md), TDD mandatory, commit discipline.
  • ORCH-QUESTIONS.md — append-only, numbered, answered inline. A worker that hits a contract problem appends and keeps working on something else; it never blocks and never patches around it.
  • Worktrees — one per worker branch. Design/research agents that write no code share the orchestrator's checkout: check git branch --show-current before every commit there.
  1. Worker hits a contract gapgoal: never patch around the contract · out: a numbered question · appends Q3 — Unlock request needs a reason field · From: ios · Blocks: the request screen, moves on
  2. Orchestrator pings yougoal: the contract only changes by your decision · you decide: "yes, optional string, max 200 chars"
  3. Orchestrator edits schemas.py, regenerates, answers inlinegoal: one change path, recorded where it was asked · out: new openapi.json + inline answer · both workers pull
  4. Checkpoint merge after verificationgoal: main only ever holds what someone other than the author has run · out: a merged branch · tests run by the orchestrator, endpoint hit by the orchestrator

Stated tradeoff: an orchestrator that also codes stops verifying — it trusts its own work — so the role is kept pure.
